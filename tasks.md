# Plan zadań: lokalny interfejs przeglądarkowy agenta wydatków

Status: ukończony (2026-11-11). Plan powstał na podstawie `requirements.md`, `design.md` i `workflow.md`; ukończono T-01–T-27, zakres P0 zamknięty.

Zakres obowiązkowy obejmuje P0: angielski interfejs, lokalny dostęp, analizę, transakcje, bezpieczne decyzje i obsługę błędów. Dokumentacja pozostaje po polsku. Plan narzędzi i integracji MCP jest w `PLAN.md`.

## Zasady realizacji

- **Statusy:** `do zrobienia`, `w toku`, `zablokowane`, `ukończone`. Wszystkie zadania poniżej zaczynają jako `do zrobienia`; `[x]` wolno ustawić dopiero po implementacji i weryfikacji.
- **Aktualizacje:** Przed rozpoczęciem zmień status na `w toku`. Po zakończeniu dopisz wynik weryfikacji; przy blokadzie zapisz przyczynę i warunek odblokowania, bez oznaczania zadania jako ukończone.
- **Pojedyncze zadanie:** Sprawdź jego zależności, wykonaj zakres, uruchom wskazane testy i zaktualizuj ten plik. Nie rozpoczynaj automatycznie kolejnego zadania, jeżeli użytkownik zlecił tylko jedno.
- **Cały plan:** Wykonuj zadania w kolejności zależności. Numery wyznaczają zalecaną kolejność, ale nie wymagają równoległej pracy ani osobnych agentów.
- **Testy przy zmianie:** Każde zadanie implementacyjne zawiera własne testy. Zadania testów przekrojowych uzupełniają je, a nie odkładają całego testowania na koniec.
- **Ochrona danych:** Używaj fixture i tymczasowych ledgerów. Nie wykonuj testowych zapisów na rzeczywistym stanie użytkownika i nie nadpisuj istniejących plików `evidence/`.
- **Zmiana zakresu:** Rozbieżność z wymaganiami lub projektem wymaga aktualizacji odpowiedniego dokumentu przed dalszą implementacją, nie cichego pominięcia kryterium.
- **Bezpieczeństwo uruchomienia:** Testowe API może działać jako aplikacja testowa w procesie. Nie uruchamiaj dostępnego serwera bez wymaganych kontroli Host, Origin, sesji i CSRF.

  - Status: ukończone.
  - Zależności: T-02, T-03.
  - Powiązania: AC-01–AC-02, AC-18; NFR-03–NFR-05, NFR-09.

  - Rezultat: lokalne UI może ustanowić sesję; obca witryna i niedozwolony host nie inicjują analiz ani zapisów.
  - Weryfikacja: poprawny bootstrap; odrzucenie brakującego, obcego lub `null` Origin przy zapisie, złego CSRF i Host; brak dostępu HTTP do `.env`, danych katalogu projektu i śladów przez static root.
  - Implementacja: `web/security.py` wprowadza middleware ASGI z dokładnym Host i Origin skonfigurowanego lokalnego endpointu. Żądania zmieniające stan wymagają istniejącej sesji, poprawnego `X-CSRF-Token`, `application/json`, prawidłowego JSON i aktualnego `instance_id`. Odrzucane są niejednoznaczne nagłówki bezpieczeństwa, powtórzone klucze JSON, niefinitywne liczby i żądania z obcym kontekstem fetch. Bufor JSON ma limit 128 KiB, mieszczący także 8000 znaków spoza BMP zapisanych jako pary sekwencji Unicode escape. Middleware nie wykonuje narzędzi domenowych.
  - Sesja: `GET /api/session` zwraca wyłącznie `csrf_token`, `instance_id` i obecnie `active_run_id=null`. Losowy cookie `expense_session` ma `HttpOnly`, `SameSite=Strict`, `Path=/`, bez Domain i bez deklaracji Secure dla lokalnego HTTP. `web/sessions.py` przechowuje losowe identyfikatory i tokeny w pamięci, z 8-godzinnym idle TTL i limitem 256 sesji; pełny magazyn daje bezpieczne 503 zamiast usuwania właścicieli. Ponowny bootstrap własnej sesji zachowuje token, a nieznanego identyfikatora nie przejmuje od klienta. Start nowego cyklu życia aplikacji rotuje `instance_id` i unieważnia poprzednie sesje.
  - Odpowiedzi i zasoby: wszystkie odpowiedzi otrzymują `Cache-Control: no-store`, CSP z zasobami wyłącznie własnego origin, `nosniff`, `DENY` dla ramek i `no-referrer`. Nie ma uprawnień CORS. Błędy walidacji i wyjątki mają bezpieczne angielskie odpowiedzi JSON bez wejścia użytkownika i surowego wyjątku; katalog uzupełniono o bezpieczne 404 i 405. `/static` wskazuje tylko `web/static`, bez listowania, dotfiles i dostępu przez dowiązania poza ten katalog; nie wystawiono katalogu projektu. Folder zawiera na razie wyłącznie znacznik `.gitkeep`, który nie jest udostępniany.
  - Instancja i CLI: osobny `WebInstanceLock` w `web/instance_lock.py` trzyma stabilny `<ledger>.web.lock` przez lifespan i odrzuca drugą aplikację lub proces dla tej samej kanonicznej ścieżki ledgera. Nie trzyma blokady domenowej i nie blokuje CLI/MCP. `.gitignore` pomija robocze pliki blokady web. CLI został odblokowany po wdrożeniu zabezpieczeń: Uvicorn otrzymuje wyłącznie `127.0.0.1`, jeden worker, `reload=False`, `proxy_headers=False` i wymagany lifespan; wyłączono access log i nagłówek serwera.
